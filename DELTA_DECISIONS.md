## 2026-09-09 — Freight Overbilling schema hardened to near-production realism; Deduction mode explicitly deferred

Raised by Venkatesh after reviewing an external (Perplexity-generated) standalone freight-audit DB schema and pushing back hard on demo-grade design: "I dont want our db to for a demo purpose having 3 or 5 columns per table that cannot meet real world requirements" / "I want the application to be ready to solve real world problems... check the internet (SAP or Oracle implementation), reddit forums and enhance the db schema."

- **Method:** verified real gaps by counting actual columns in the live migration files directly (not assuming), then researched real enterprise patterns — SAP TM's fuel-surcharge index/escalator/peg model, Oracle OTM's Rate Offering → Rate Geo → Cost/WeightBreak/UnitBreak/Accessorial hierarchy, and freight-audit industry guides (core principle: "match invoice lines to shipment facts, not to the invoice itself").
- **Scope decision:** Venkatesh narrowed scope explicitly — "Our initial focus is on Freight Overbilling so let us ensure that the schema is close to real (95%)." Deduction-mode (CPG/retailer) gaps found in the same research (promotional/scan-based/price-protection/damage/slotting deduction categories, each with specific evidence requirements) were identified but NOT built — out of current scope, not forgotten. Revisit when Deduction mode is prioritized.
- **What shipped:** `supabase/migrations/20260909000001_freight_overbilling_hardening.sql` — see [[DELTA_STATE]] for the full table/column breakdown. Net new: `fuel_surcharge_indices`, `fuel_surcharge_schedules`, `shipment_items`, `accessorial_events`. Widened: `contract_lines`, `shipments`, `invoice_charges`.
- **Why a real fuel surcharge table, not a flat amount:** a flat billed fuel surcharge can't be audited — there's nothing to compare it to. SAP TM's model (a published index + a per-contract formula) makes the correct value *computable*, which is what turns FUEL_SURCHARGE_ERR from an assignable reason code into a verifiable one.
- **Why `shipment_items` at line level, not just `shipments` totals:** freight class/reweigh disputes are inherently line-level (NMFC code, declared class, dimensions) — a shipment-level total can't support a reclass argument.
- **Scratch-tested 2026-09-09 on local `delta_dev` — 3 real bugs found and fixed, not cosmetic:**
  1. **Apostrophe-escaping corruption in transfer.** 5 instances of `''` (SQL's escaped single quote) inside `COMMENT ON ... IS '...'` string literals were silently collapsed to a single `'` somewhere in the base64-encode/decode transfer from the cloud session to the linked device. This broke the string literal itself (`ERROR: syntax error at or near "s"`), not just a cosmetic typo — the migration would not run at all until fixed. Lesson: any text transfer of SQL containing escaped quotes needs a post-transfer diff/grep check for `''`, not just a line-count check.
  2. **Missing `unique (tenant_id, id)` on new FK-target tables.** House convention (`20260826000012_composite_tenant_fks.sql` and every subsequent migration) requires this constraint on any table referenced via the composite-FK pattern. `fuel_surcharge_schedules` (referenced by `invoice_charges.fuel_surcharge_schedule_id`) was missing it — added, along with the same constraint on `shipment_items`, `accessorial_events`, and `fuel_surcharge_indices` for consistency even though nothing FKs to the latter two yet.
  3. **`users` table never had this constraint at all — a genuine pre-existing gap, not introduced by this migration.** Checked `20260826000012_composite_tenant_fks.sql`: `users` is absent from that original sweep. No prior migration ever referenced `users` via a composite FK, so the gap was latent until `accessorial_events.approved_by` became the first to need it. Added `alter table users add constraint uq_users_tenant_id unique (tenant_id, id);` directly in this migration rather than opening a separate fix-up migration, since it's a one-line prerequisite for this migration's own FK.
- **Status: scratch-tested and passing on `delta_dev`. NOT YET applied to `wim_dev`.** Pending Venkatesh's own terminal per the standing Postgres-egress constraint (see [[DELTA_PLAN]]).
- **Linear:** AS2-46 scope updated to reference the new structured tables (was written before this hardening pass existed).

## 2026-09-09 — Freight Overbilling: two day-to-day gaps closed, evidence-sourcing gap explicitly deferred

Raised by Venkatesh after reviewing the proposed AS2-54 comparator ladder against the hardened schema: "Will this algo meet real life business requirements" → "I dont want to over complicate but I would like to make sure that our solution meets most of the day to day requirements."

- **Three gaps identified** when checking the comparator ladder against real freight-audit practice: (1) no contract-level accessorial rate/free-time schedule — `accessorial_events.free_time_minutes` was self-reported with nothing to verify it against; (2) `accessorial_events` tied to `shipment_id`, inconsistent with `proof_of_delivery`'s correct leg-level pattern, losing carrier attribution on interline shipments; (3) no independent evidence source for gate timestamps or mileage — both are effectively self-reported by/derived from the carrier's own documents, so rate-math checks pass even if the underlying facts are fabricated.
- **Decision — build (1) and (2), defer (3).** (1) and (2) are schema-only, cheap, and close the single most common everyday dispute category (detention/accessorial rate or free-time mismatch) and a real correctness bug (wrong-carrier attribution). (3) requires an external data source (telematics, WMS, a mileage-rating API) — a genuine integration/spend decision, not a schema fix, and out of scope for "meets day-to-day requirements without over-complicating." The auto-approve gate already sends anything lacking sufficient evidence to manual review, so (3) being unsolved doesn't mean bad data gets silently trusted — it just means the system can't independently disprove a fabricated timestamp/mileage figure yet.
- **What shipped:** `supabase/migrations/20260909000002_accessorial_rates_and_leg_level.sql` — `carrier_accessorial_rates` (new, per-contract rate/free-time terms by code, `EXCLUDE USING GIST` overlap protection matching the `fuel_surcharge_schedules` pattern), `accessorial_events.shipment_id` → `shipment_leg_id`, and a new `accessorial_events.carrier_accessorial_rate_id` FK. Scratch-tested on `delta_dev`, applied to `wim_dev`.
- **Not solved, explicitly deferred, tracked in [[DELTA_PLAN]]:** independent evidence sourcing for gate timestamps and mileage. Revisit if/when telematics or a WMS integration becomes viable — do not build a workaround (e.g. trusting a self-reported field as if it were independent) in the meantime.

## 2026-09-07 — Extraction OCR path: free-tier OpenRouter vision model, not Azure Document Intelligence (yet)

Confirmed by Venkatesh in a Cowork session, scoping the Ingestion agent's extraction handler (AS2-12/13).

- **No OCR/Document Intelligence client exists anywhere in the codebase.** The architecture doc's tiered-extraction design (originally drafted this session, see the docx `4.9a`) assumed Azure Document Intelligence for Tier 1/2 OCR. That integration was never built, and provisioning it is a real spend/infra decision gated by DELTA_CONSTRAINTS — not something to build toward without approval.
- **Decision: use a free (`:free` suffix), vision-capable model via OpenRouter as the OCR/extraction path for scanned, handwritten, or image-based documents, for now.** This is $0 spend under OpenRouter's free tier and needs no infra provisioning — it reuses the existing `packages/shared/src/llm/openrouter.ts` client (extended to accept an image/multimodal payload) rather than adding a new Azure integration. Explicitly scoped as a v1/testing measure, not a permanent architecture decision — Document Intelligence remains the intended path once real customer volume outgrows free-tier rate limits (20 requests/minute; 50/day with no credits ever purchased on the account, 1,000/day once $10 has been — see https://openrouter.ai/docs/api_reference/limits, verify current numbers before relying on them since this is OpenRouter policy, not our code).
- **Do not hardcode a specific free model ID in code or prompts.** OpenRouter's free-model roster changes over time. The extraction handler queries OpenRouter's live model catalog and selects a currently-available free model with image input support, via the existing `OPENROUTER_MODEL_EXTRACTION` env var — config, not a code change, consistent with the existing routing pattern (2026-08-31 entry below).
- **Deterministic verification pass added for Tier 1/2 (text-native documents), no added cost.** After AI extraction, check whether the extracted value literally appears (whitespace/case-normalized) in the text that was already pulled out by a plain, non-AI PDF-text-extraction step. This is ordinary code — the "ground truth" text exists independently of the AI call in both Tier 1 (no AI call at all) and Tier 2 (AI runs on that same pre-existing text) — so it catches hallucinated values (AS2-11's concern, see the Obsidian wiki's `OpenRouter-Model-Routing-and-LLM-Strategy.md`) at zero extra rate-limit or dollar cost. Recorded as `extraction_fields.verified` (new column).
- **No equivalent free verification exists for Tier 3 (image-only/scanned documents).** The vision model both reads the page and extracts the value in one call — there's no independent text layer to check it against without a second AI call, which isn't worth the free-tier budget it would cost. Tier 3 output is always `verified = null` and flagged for mandatory human review by default, rather than pretending it's been checked.
- **Correction to earlier scoping this session:** an initial draft of the extraction-handler build prompt flagged `documents.doc_type` as missing a `'pod'` value. That's stale — `20260906000004_bol_pod_freight_docs.sql` already added `'pod'` to the CHECK constraint. All 7 values are valid today; no workaround needed.

**What this does NOT cover:** the AS2-11 "extraction guardrails" idea from the wiki (bounding-box source-locator, "highlighter not pen" style hallucination prevention) is broader than the string-containment check built here — worth its own follow-up if extraction accuracy becomes a customer-facing trust issue, not built in this pass.

## 2026-09-06 — Freight Overbilling doc coverage: BOL and POD given structured tables, PO<->shipment link closed

Raised by Venkatesh: given the 5 stated Freight Overbilling inputs (PO, Rate Contract, BOL, POD, Carrier Invoice), checked whether the schema has entities/tables for all of them (foundational datasets excluded).

- **Findings:** PO (`orders`/`order_lines`) and Rate Contract (`contracts`/`contract_lines`) and Carrier Invoice (`invoices`/`invoice_lines`/`invoice_charges`) were already well covered. Two real gaps: (1) `shipments` had no FK back to `orders` -- a shipment/invoice could only reach its PO via `invoices.order_id`, not directly; (2) Bill of Lading was only a bare `shipments.bol_number` text field, and Proof of Delivery had **zero** representation anywhere (no `'pod'` value in `documents.doc_type`, `reference_numbers.reference_type`, or `document_references.reference_type` -- closest proxy was `shipment_legs.actual_delivery_at`, a bare timestamp with no signature/exception/shortage capture).
- **Venkatesh's explicit requirement:** these must be proper RDBMS tables, not reliance on the generic `documents`/`extractions` unstructured-extraction pipeline -- needed for clean, repeatable SQL joins (the actual overbilling detection logic: billed vs. contracted vs. actually delivered).
- **Logical data model reviewed via PDF before build**, three rounds of correction from Venkatesh:
  1. `shipments.carrier_id` is single-valued (M:1) -- correctly flagged as a possible gap, but resolved as already-solved: `shipment_legs.carrier_id` is the existing M:N mechanism for multi-carrier/interline shipments. Documented via a comment on `shipments.carrier_id` rather than a schema change.
  2. **POD tied to `shipment_leg_id`, not `shipment_id`** -- since carrier assignment is M:N at the leg level, a delivery event belongs to the specific carrier's leg, not the shipment as a whole.
  3. **BOL<->shipment made N:M via a junction table** (`bill_of_lading_shipments`), not a direct FK -- a consolidated LTL load can share one BOL across multiple shipments; a split shipment can span multiple BOLs.
- **What shipped:** `supabase/migrations/20260906000004_bol_pod_freight_docs.sql` -- `shipments.order_id` (nullable FK -> orders), `bills_of_lading` (structured BOL), `bill_of_lading_shipments` (N:M junction), `proof_of_delivery` (per-leg, `shortage_qty`/`shortage_uom` CHECK-gated to short/damaged/partial statuses only), plus `'pod'` added to `documents.doc_type` and `reference_numbers.reference_type`.
- **Tested:** 6 scenarios on scratch Postgres (order_id FK insert, N:M junction insert, two PODs on two legs of one shipment, shortage-on-non-exception-status correctly rejected by CHECK, `'pod'` doc_type accepted, audit trigger fires on all 3 new tables) -- all pass. **Applied for real to `wim_dev`** by Venkatesh directly (neither the cloud session nor the linked-device shell has raw TCP egress to Supabase's Postgres port -- HTTPS/npm only -- so `node scripts/postgres.mjs migrate` had to be run by Venkatesh in his own terminal, same constraint noted for future sessions). Verified directly via `psql`: 3 tables present, audit trigger firing on all 3.
- **Not yet decided / follow-up:** whether `shortage_qty` needs its own UOM independent of `shortage_uom` added here (resolved: `shortage_uom` added directly, no gap); retention/versioning if a POD is corrected after capture (superseded row vs. update -- audit trigger already logs before/after either way, not further decided).

## 2026-09-06 — Who/what/when history added, via a generic audit trigger rather than per-entity SCD-2

Raised by Venkatesh: "Definitely we need type-2 SCD - we need to keep history -- who, what, when etc," triggered by the data-model-scrutiny discussion (what would a customer/VC/PE technical review flag).

- **Two design options presented, decided together:**
  1. **Approach — history table per entity vs. one generic table.** True Kimball SCD-2 (each change = new row, new surrogate key, FKs resolve through a "current version" lookup) was ruled out: it would require rewriting every FK across ~15+ tables that reference `retailers`/`carriers`/etc. directly by a stable `id` — invasive, and nothing in DELTA needs point-in-time joins, only "what changed and who changed it." A dedicated history table per entity (`retailer_history`, `carrier_history`, ...) was the initially preferred shape, but at the chosen scope (77 tables) that would mean ~77 new, nearly-identical tables — engineering judgment call made instead: one generic `fn_audit_log_change()` trigger reusing the `audit_log` table already built in AS2-53 (previously unused), which has the exact `entity_table`/`entity_id`/`before`/`after` shape needed. Flagged to Venkatesh as a deviation from the literal answer given; not re-confirmed beyond the migration delivery.
  2. **Scope — chosen: "everything tenant-scoped."** Applied to all 77 tables with both `tenant_id` and `id` (plus `tenants` itself, special-cased). Excluded: `audit_log` (would recurse), `usage_events`/`dq_results`/`webhook_deliveries` (already insert-only event/telemetry streams — auditing them would duplicate their own rows for no benefit).
- **"Who":** reads an `app.actor_user_id` session GUC, same pattern as `current_tenant_id()`/`app.tenant_id` already used for RLS. Falls back to `'system'` when unset. **Real gap: not wired into any application code yet** — this session was schema-only. Every audit row will say `actor='system'` until an agent's request-handling code actually runs `SET LOCAL app.actor_user_id = '<users.id>'`. Tracked in [[DELTA_PLAN]] as a required follow-up before this audit trail is actually useful for "who."
- **Found and fixed a second, unrelated gap while building this:** `retailers`/`carriers` never had `trg_set_updated_at` wired (missed in the 2026-09-02 retailer/carrier split) — `updated_at` had been silently stuck equal to `created_at` for both tables since creation. Bundled into the same migration since it uses the identical trigger-wiring pattern.
- **Migration:** `supabase/migrations/20260906000003_generic_audit_trail.sql`. Tested via 6 scenarios on scratch Postgres (actor default/override, INSERT/UPDATE/DELETE before/after semantics, `tenants` special-case, exclusion list correctness) — all pass. **Applied for real to `wim_dev`** — verified directly: 77 distinct tables carry the audit trigger.

## 2026-09-06 — Retailer/Carrier address model: HQ and Bill-To/Remit-To kept as two distinct sets of columns

Raised by Venkatesh in response to a multi-tenant concern (one org can have multiple businesses as customers, each with different addresses/ship-to/bill-to). Confirmed and applied for real.

- **Context:** `retailers`/`carriers` (post the 2026-09-02 split) carry no address fields at all — only `name`, `legal_name`, `country_code`. Addresses only existed via `locations` (operational sites: warehouses, stores, terminals, yards) or per-shipment via `shipment_counterparties.role`. There was no canonical "this retailer's own HQ/billing address" independent of any operational site or shipment.
- **Decision:** add two distinct address sets directly on each table, not a shared address block and not another `locations` row:
  - `retailers`: `hq_*` (6 columns) + `bill_to_*` (6 columns) + `bill_to_same_as_hq` (app-layer convenience flag, not constraint-enforced) — 13 new columns total.
  - `carriers`: `hq_*` (6 columns) + `remit_to_*` (6 columns, the carrier-side analogue of Bill-To — carriers are OVERBILLING mode, they invoice us, we remit payment to them) + `remit_to_same_as_hq` — 13 new columns total.
  - Both sets fully nullable except the same-as-hq flags (default `false`); retrofits existing rows with no address data. RLS's existing row-level `tenant_isolation` policy covers the new columns automatically — no policy change needed.
  - Scoped to `retailers` first per Venkatesh's explicit ask, then mirrored to `carriers` for symmetry (same gap existed there) once confirmed.
- **Migrations:** `supabase/migrations/20260906000001_retailer_hq_and_bill_to_address.sql`, `20260906000002_carrier_hq_and_remit_to_address.sql`. Both tested against the full migration chain replayed on scratch Postgres (0 errors) before applying. **Applied for real to `wim_dev`** — verified directly via `psql`: `inet_server_addr()` confirmed non-local, 13 new columns present on each of `retailers`/`carriers`.

## 2026-09-04 — `document_references` vs `reference_numbers`: not duplicates, kept separate

Resolved by inspecting both migrations directly (`20260826000008_reference_numbers.sql`, `20260903000001_schema_part2_operational.sql`), closing the open question flagged since AS2-52 (2026-09-02).

- **`reference_numbers` (AS2-6):** a resolved, polymorphic reverse-lookup registry. `entity_table` + `entity_id` points at whatever real row already owns a given reference value, across many entity types (po/bol/pro/asn/load/container/seal/invoice/shipment/claim). Built *after* a value has been matched to something.
- **`document_references` (AS2-52):** scoped only to `invoices` (real FK, not polymorphic), and captures what an invoice *asserts* about another document — e.g. "this invoice cites PO #X" — as raw extracted text, before/independent of that citation being resolved to a real row. Narrower reference-type set (po/despatch_advice/receipt/contract/bol/other).
- **Decision: these are different pipeline stages, not the same concept.** `document_references` = unverified claim at extraction time; `reference_numbers` = verified pointer at resolution time. Keep both tables as-is, no merge.
- **Real gap identified (not resolved, needs a design call):** nothing currently promotes a `document_references` row into `reference_numbers` once it's matched, and nothing marks a `document_references` row as resolved/unresolved. See [[DELTA_PLAN]] for follow-up.

## 2026-09-02 — AS2-53 (schema part 3: links/settlement/reconciliation/ops) built, tested, and applied for real to Supabase

Built and applied in a Cowork session, confirmed by Venkatesh.

- **`supabase/migrations/20260904000001_schema_part3_reconciliation.sql`** — **29 new tables** across 5 groups: Links/allocation/inference (`match_links`, `fulfilment_balances`, `equivalences`, `variance_conditions`, `dispute_items`, `adjustments`, `adjustment_allocations` — 7), Settlement & deductions (`payments`, `remittance_advices`, `remittance_lines`, `deductions` — 4), Reconciliation & dispute (`match_profiles`, `reconciliations`, `reconciliation_lines`, `reconciliation_evidence`, `disputes`, `dispute_events`, `recoveries` — 7), Ops & governance (`api_keys`, `webhook_subscriptions`, `webhook_deliveries`, `dq_rules`, `dq_results`, `audit_log`, `import_jobs`, `onboarding_state` — 8), Derived (`leakage_events`, `recovery_metrics`, `reconciliation_trends` — 3). `usage_events` already existed from AS2-9 (2026-08-31) and was the only table in the ticket's original scope not newly created.
  - **Correction:** initial docs and Linear comments said "21 new tables" — a miscount. The correct figure is 29, matching the group breakdown above. The AS2-53 ticket title itself ("22 entities") doesn't match its own group totals either — a pre-existing inconsistency in the ticket, not introduced this session.
- **Four sum-integrity CHECK constraints**, each backed by an `AFTER INSERT OR UPDATE` trigger since Postgres CHECK can't reference sibling rows: `match_links.allocation_pct` per (from_table, from_id) sums ≤ 1 across active links — no double-counted money; `variance_conditions.contributes_amount` per reconciliation sums ≤ |delta_amount|; `adjustment_allocations.amount` per adjustment sums ≤ adjustment.amount; `deductions` has a plain CHECK `deducted_amount = invoiced_amount - paid_amount` (single-row, no trigger needed).
- **`match_links` never deletes — corrections supersede.** A partial unique index enforces one active link per (from_table, from_id, to_table, to_id) `where status = 'active'`; a correction sets the old row's `status = 'superseded'` and `superseded_by`, then inserts a new active row. Chain stays walkable via `superseded_by`.
- **`recompute_fulfilment_balance(tenant_id, order_line_id)`** — driven only by currently-active `match_links` rows (excludes superseded), upserts into `fulfilment_balances`. Not a trigger — called explicitly after a `match_links` change, same pattern as the rest of the schema (no auto-cascading recompute logic yet).
- **Polymorphic entity references** (`match_links.from_table/from_id`, `dispute_items.entity_table/entity_id`, etc.) use the same `entity_table text + entity_id uuid` pattern as `document_links`/`reference_numbers` (AS2-6/52) rather than typed FKs, since they must point at any of several line-item tables. Postgres can't enforce a polymorphic FK — same accepted tradeoff as those two tables.
